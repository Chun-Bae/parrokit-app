# AGENTS.md

이 프로젝트는 빠르게 만들고 실제로 사용하면서 다듬는 방식으로 개발한다.
아키텍처와 코드 스타일보다 사용자 요청과 동작하는 결과를 우선한다.

## 우선순위

1. 사용자 요청
2. 이 파일의 최소 규칙
3. 기존 코드와 `docs/agents/rules/*`, `docs/agents/workflows/*`의 참고 지침

세부 rules와 workflows는 강제 규칙이 아니다. 현재 작업에 도움이 되는 부분만 참고한다.
스킬은 작업에 필요하거나 사용자가 요청한 경우 적용한다.

## 개발 방식

- MVVM, Clean Architecture, 레이어별 폴더 분리, Provider와 UseCase 사용을 강제하지 않는다.
- 작은 기능은 한 파일에서 시작해도 된다. 실제 복잡성이나 재사용 필요가 생기면 나눈다.
- Widget 안의 로컬 상태와 간단한 동작 로직을 허용한다.
- import 순서, 네이밍 형식, 주석 형식, 파일 길이를 별도 규칙으로 강제하지 않는다.
- UI 값은 직접 지정해도 된다. 기존 테마 사용과 새 디자인 모두 허용한다.
- 리팩터링은 요청된 목적에 맞는 코드 정리로 해석한다. 아키텍처 재설계를 기본으로 요구하지 않는다.
- 매 작업마다 상세 설계 문서, ADR, 변경 이력, 테스트 파일을 만들 필요는 없다.
- 변경 범위가 크거나 기존 기능과 데이터에 영향을 주면 핵심 접근과 영향을 먼저 설명한다.

## 지켜야 할 최소 규칙

- 요청 범위 밖 기능 변경이나 무관한 정리, 대규모 포맷 변경은 하지 않는다.
- 기존 기능과 사용자 데이터를 임의로 삭제하지 않는다.
- 실험 화면을 별도 파일로 요청하면 원본을 유지하고 전환 지점을 명확히 둔다.
- 비동기 작업 뒤 UI를 사용할 때는 필요한 mounted 검사와 자원 해제를 지킨다.
- 키, 토큰, 비밀번호와 민감한 사용자 데이터를 코드나 로그에 남기지 않는다. `.env`는 커밋하지 않는다.
- 인증과 접근 제어는 최소 권한을 유지한다.
- 생성 파일은 도구로 필요한 경우에만 갱신한다.
- 사용자 요청 없이 커밋, 푸시, 배포를 자동으로 진행하지 않는다.

## 검증

- Dart/Flutter 코드 변경 후 가능한 범위에서 `flutter analyze`를 실행한다.
- 변경에 맞는 최소한의 빌드, 실행 또는 테스트를 선택한다. 단순 UI 변경마다 테스트 작성을 강제하지 않는다.
- DB와 모델 변경 시 마이그레이션과 코드 생성 필요 여부를 확인한다.
- 검증하지 못한 내용과 알려진 한계는 사실대로 보고한다.

## 하네스 변경

- 사용자가 요청하거나 명시적으로 승인하면 이 파일과 관련 rules, workflows를 직접 수정할 수 있다.
- 사용자 요청 없이 강제 규칙을 추가하거나 하네스를 확장하지 않는다.
- 실제 관리 파일은 `docs/agents/` 아래에 있다. 기존 심볼릭 링크는 유지한다.

## 완료 보고

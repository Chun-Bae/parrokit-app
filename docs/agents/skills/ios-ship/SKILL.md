# iOS Ship (빌드 번호 올리기 + 릴리스 노트 + 배포)

`ios-distribute`는 빌드와 업로드 자체를 다룬다. 이 스킬은 그 앞뒤를 맡는다 —
**지난 배포 뒤에 바뀐 것만** 골라 개조식으로 적고, 빌드 번호를 올리고, 노트와
함께 올린다.

사용자가 배포를 요청하면 묻지 말고 아래를 순서대로 실행한다.

## 1. 지난 배포 지점 찾기

빌드 번호를 올린 커밋이 배포 지점이다. 이 저장소는 그 커밋을
`chore(release): 빌드 번호를 N으로 올린다`로 적는다.

```bash
git log -1 --format=%H --grep='^chore(release)'
```

못 찾으면 사용자에게 어디부터인지 묻는다. 추측해서 전부 적지 않는다 —
노트가 지난번과 겹치면 테스터가 무엇이 새것인지 모른다.

## 2. 바뀐 것 모으기

```bash
git log --reverse --format="%s" <그 커밋>..HEAD
```

## 3. 개조식으로 추리기

**테스터가 앱에서 보거나 눌러 볼 수 있는 것**만 적는다. 다음은 빼거나 한 줄로
묶는다: 테스트 추가, 스크립트 손질, 주석·이름 바꾸기, 거울 테스트.

- 명사형으로 끝낸다. '~했습니다'가 아니라 '~ 통합', '~ 수정'.
- 묶음 제목을 두고 그 아래 `- `로 나열한다.
- 한 줄에 한 가지. 왜 고쳤는지는 보이는 결과로 적는다.
- 서버만 바뀐 것은 `서버` 묶음으로 따로 둔다. 앱을 다시 깔아도 안 보이는
  것이라 테스터가 헷갈린다.

노트는 scratchpad에 파일로 적고 `--release-notes-file`로 넘긴다. 셸에서
따옴표로 넘기면 줄바꿈과 가운뎃점이 깨진다.

## 4. 빌드 번호 올리기

`pubspec.yaml`의 `version: 1.0.6+N`에서 N만 1 올린다. 버전(1.0.6)은
사용자가 말할 때만 바꾼다.

같은 번호로 또 올리면 App Distribution 목록에 같은 이름이 둘 생기고, 이미
깐 기기는 업데이트로 보지 않는다.

올린 뒤 `chore(release): 빌드 번호를 N으로 올린다`로 커밋한다. 다음 배포가
이 커밋을 지점으로 쓴다.

## 5. 빌드

10~20분 걸린다. 백그라운드로 돌리고 로그를 파일로 받는다.

```bash
flutter build ipa --release --export-method ad-hoc
```

실패하면 `ios-distribute`의 진단 표를 본다. 추측하지 말고 로그에서
`error`, `No profiles`, `does not` 줄을 찾는다.

## 6. 업로드

IPA 이름은 추측하지 말고 `ls build/ios/ipa/`로 확인한다.

```bash
npx -y firebase-tools@latest appdistribution:distribute build/ios/ipa/*.ipa \
  --app 1:392832464036:ios:71b3e2d9c65fa1922e6231 \
  --groups testers \
  --release-notes-file <노트 파일 경로>
```

## 7. 알리기

업로드 출력의 버전·빌드 번호가 의도한 것인지 보고, 릴리스 링크를 전한다.
**폰에 설치되는 것까지는 확인한 것이 아니다.** 설치는 사용자가 본다.

## 지킬 것

- 커밋·푸시는 이 스킬이 하는 빌드 번호 커밋 하나뿐이다. 다른 것은 건드리지
  않는다.
- 키·토큰·비밀번호를 노트나 로그에 적지 않는다.
- 빌드 전에 `flutter analyze`와 `flutter test`를 돌린다. 깨진 채로 올리지
  않는다.

Parrokit 4차: UI/UX 개편. 사용자는 자거나 회사에 있어서 거의 못 본다. 시간과 토큰을 아끼지 않아도 된다. 판단이 필요한 것은 기록만 하고 계속한다. 사용자가 멈출 때까지 끝내지 않는다.

상태 파일 (매 반복 시작 시 먼저 읽는다)
- .claude/round4-audit.md: 맨 위 요약(항상 최신), 작업 목록, 진행 기록, 보류, 안건
- .claude/design-research.md: 레퍼런스 조사. 앱, 화면, 패턴, 출처 URL, 우리 앱에 쓸 점
- .claude/design-direction.md: 디자인 원칙과 화면별 개편안(결정과 이유)
- 참고: .claude/round3-audit.md, .claude/clip-redesign.md, .claude/feature-proposals.md
- 스크린샷은 .claude/round4-shots/ 에 저장한다. 커밋하지 않는다. .git/info/exclude에 있는지 확인한다

0단계 (처음 한 번만)
1. flutter analyze, flutter test, functions의 npm run lint와 build로 기준선을 round4-audit.md에 적는다
2. 시뮬레이터로 지금 앱의 모든 탭과 주요 하위 화면을 라이트로 찍어 개편 전 기준으로 남긴다
3. 화면마다 사용성 점검을 적는다: 3초 안에 다음 행동이 보이는가, 글이 너무 많은가, 같은 역할인데 모양이 다른가, 대비와 글자 크기와 44pt 터치 영역, 빈 상태와 로딩과 오류

1단계: 레퍼런스 조사 (반복 몇 번에 나눠도 된다)
- WebSearch와 내장 브라우저로 로그인 없이 볼 수 있는 자료만 본다: App Store와 Google Play 스크린샷, 디자인 사례 글, 공개 포트폴리오. 로그인이 필요한 사이트는 건너뛴다. 쿠키 창은 필수만 허용한다. 파일은 내려받지 않는다
- 볼 것: 언어 학습 앱(말하기, 복습, 진행감), 영상과 클립 보관, 플레이어, 짧은 영상 피드, 커뮤니티 Q&A, 국내 생활 앱의 설정, 지갑, 목록 화면
- design-research.md에 화면 종류별로 정리한다: 어떤 패턴인가, 사람에게 왜 도움이 되는가, 출처 URL, 우리 앱 어디에 쓸 수 있는가
- 특정 앱의 생김새, 브랜드, 그림, 문구를 그대로 베끼지 않는다. 패턴만 가져와 우리 앱(브랜드 파랑 0064FF, 앵무새 캐릭터)에 맞게 새로 만든다

2단계: 방향 정하기
- design-direction.md에 원칙 5~8개를 적는다. 예: 한 화면 한 목적, 다음 행동은 크게 하나, 설명 대신 바로 해볼 수 있게, 진행감 보이기, 카드보다 목록
- 화면별 개편안을 우선순위대로 적는다: 홈, 학습(무대와 학습 허브), 보관함, 커뮤니티, 플레이어와 쇼츠, 콘텐츠 제작, 더보기 하위 화면
- 개편안마다 바꾸기 전 문제, 바꿀 모습, 참고한 패턴, 위험을 적는다

3단계: 개편 (반복)
- 큰 개편(배치나 구성이 바뀌는 것)은 원본 파일을 두고 새 파일로 만든다. AppConfig에 newDesign 스위치를 하나 두고, 더보기의 앱 묶음에 "새 디자인" 스위치로 켜고 끈다. 기본값은 켬. 스위치를 끄면 그 화면들이 원래대로 돌아와야 한다
- 작은 정리(간격, 글 줄이기, 색, 대비, 같은 모양 맞추기)는 원본에 바로 해도 된다
- 기능과 데이터 흐름은 그대로 둔다. 버튼이 하던 일, 저장하는 곳, 서버 호출은 바꾸지 않는다
- 화면마다 바꾸기 전과 후를 라이트와 다크로 찍어 비교한다. 겹침, 잘림, 대비 문제가 없을 때만 커밋한다
- 한 커밋에 한 화면 또는 한 공용 컴포넌트. 메시지에 무엇이 문제였고 무엇을 참고해 어떻게 바꿨는지 쓴다

계속 할 일이 떨어지면
- 바뀐 화면을 다시 돌며 사용성 점검을 반복하고, 더 나은 안이 있으면 개편안에 추가한다
- 이전 보류 UI('코인' 문구, 활동 카드 '일반' 칩, 공감 아이콘 통일, 로그아웃 상태 질문 화면, 흐린 '서버' 아이콘)와 작은 기능(같은 탭 다시 누르면 첫 화면, 질문 '전체' 필터, 말하기 설정 시트의 더하기 버튼을 문장 추가 흐름에 연결)도 처리한다
- 레퍼런스 조사를 더 넓힌다
- 테스트가 없는 중요한 로직에 테스트를 더한다

매 반복
1. 상태 파일을 읽고 다음 항목 하나를 고른다
2. 작업하고, flutter analyze와 flutter test가 깨끗해야 다음으로 간다. 시뮬레이터로 확인하고 커밋한다
3. round4-audit.md의 진행 기록과 맨 위 요약(바뀐 것, 스위치로 볼 수 있는 화면, 미확인, 보류, 안건)을 갱신한다

절대 하지 말 것
- git push, firebase deploy
- pubspec.yaml의 version(버전 이름과 +빌드 번호) 바꾸기. iOS 배포 워크플로가 이 값을 그대로 쓰므로 사용자가 배포할 때 직접 올린다
- 커밋 메시지에 Co-Authored-By 넣기
- 기능 삭제, 데이터 흐름이나 저장 방식 변경, DB 스키마나 마이그레이션 변경
- 로그아웃, 계정 설정 변경, 원래 있던 사용자 데이터 삭제, 실제 커뮤니티에 쓰기나 추천이나 투표, 공유나 결제나 광고 버튼 실제로 누르기
- 웹사이트 로그인, 회원가입, 파일 내려받기, 폼 제출
- 지금 배포된 서버와 규칙에서 앱이 깨지는 변경
- analyze나 test가 깨진 상태로 커밋하기
- 확인 못 한 UI 변경 커밋하기. 보류로 남긴다
- 키, 토큰, 비밀번호를 코드나 로그에 남기기

시뮬레이터
- flutter build ios --simulator --debug, 440x956 points, 탭은 duration 0.15
- 입력은 xcrun simctl pbcopy booted로 붙여넣는다
- 확인 뒤 앱 테마와 시뮬레이터 외형은 라이트로 되돌린다

끝내는 조건
없다. 사용자가 멈출 때까지 계속한다. 할 일이 없어 보여도 "계속 할 일이 떨어지면"으로 간다.

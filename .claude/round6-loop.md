Parrokit 6차: **출시해도 되는 상태로 만든다.** 사용자는 자거나 회사에 있어 거의 못 본다.
판단이 필요한 것은 기록만 하고 계속한다. 사용자가 멈출 때까지 끝내지 않는다.

5차와 무엇이 다른가
- 5차는 화면을 다듬고 글귀를 맞추는 일이었다. **6차는 그걸 하지 않는다.**
- 찾을 것은 **돈과 데이터와 심사**다. 사용자가 손해를 보거나, 앱이 스토어에서
  반려되거나, 운영자가 법적으로 노출되는 것.
- 글귀가 어색하다, 여백이 어긋난다, 빈 화면이 밋밋하다 — 6차에서는 **적지도 않는다.**

상태 파일 (매 반복 시작에 먼저 읽는다)
- `.claude/round6-audit.md`: 출시를 막는 것, 배포 필요, 바뀐 것, 안건, 진행 기록
- `.claude/round5-audit.md`: 5차에서 넘어온 '배포 필요'와 '안건'. 평소에는 읽지 않고
  6차 파일에 옮겨 적은 것만 본다
- 참고: `.claude/review-findings.md`(3차 리뷰 결과), `.claude/subscription-plan.md`

반복 주기
- 30분마다. 앞 반복이 끝나야 다음이 시작된다.

무엇을 먼저 보나 (위에서부터)

1. **돈** — 결제·구독·지급·환불. 사용자가 돈을 냈는데 못 받는 길, 안 내고 받는 길,
   두 번 받는 길. RevenueCat 웹훅이 안 왔을 때 복구할 방법이 있는지. 장부(`applyLedger`)의
   멱등 키가 실제로 모든 지급 길에 붙어 있는지. 환불 회수가 잔액보다 많을 때.
2. **데이터 유실** — 사용자가 쌓은 것이 조용히 사라지는 길. 오늘(11-25)만 둘 나왔다
   (`initUserDocument`의 merge set, 탈퇴 중간 실패). 같은 모양이 더 있는지.
3. **심사 반려** — 애플 가이드라인에 걸리는 것. UGC 필터, 구매 화면 고지, 죽은 버튼,
   권한 설명문.
4. **보안·권한** — `firestore.rules`가 실제로 막는지. 서버 전용 칸을 앱이 쓸 수 있는지.
   남의 것을 읽거나 고칠 수 있는지.
5. **배포 어긋남** — 저장소 코드와 돌고 있는 서버가 다른 것. 고쳐 놓고 안 나간 함수.

어떻게 찾나
- **코드를 읽어서 찾는다.** 시뮬레이터로 화면을 훑는 방식은 6차에서 주된 방법이 아니다.
  고친 것을 확인할 때만 쓴다.
- 돈이 오가는 길은 **양쪽을 다 본다**: 앱(`lib/`)이 무엇을 믿고, 서버(`functions/src/`)가
  무엇을 정하는지. 둘이 다르면 그게 결함이다.
- **단정하기 전에 잰다.** 오늘만 두 번, 버그로 보였던 것이 재 보니 아니었다
  (`du`가 APFS 압축 블록을 센 것, 쇼츠 시험 클립이 실제로 검은 영상인 것).
  로그·파일·실제 값을 먼저 확인하고 적는다.

매 반복
1. `round6-audit.md`를 읽고 '출시를 막는 것'에서 위부터 한 조각을 고른다
2. 고치고 `flutter analyze`와 `flutter test`가 깨끗해야 넘어간다.
   `functions/`를 바꿨으면 `npm run build`와 `npm run lint`도 본다
3. `round6-audit.md`에 적고 커밋한다(한 커밋에 한 조각, 메시지에 문제·바꾼 것·확인한 것)

지킬 것
- 사용자 요청 없이 커밋·푸시·배포를 자동으로 하지 않는다. 배포가 필요하면
  '배포 필요'에 적어 둔다.
- 키·토큰·비밀번호를 코드나 기록에 남기지 않는다.
- 기존 기능과 사용자 데이터를 임의로 지우지 않는다.
- 확인하지 못한 것은 확인하지 못했다고 적는다.
